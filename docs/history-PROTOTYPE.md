# 历史记录与关联回放：界面原型

这是 throwaway 原型，保存在 `codex/prototype-watch-history`，不属于正式版。它要回答的问题是：能否从历史 NPU 占用，沿着同轮 PID 找到当时的进程命令和工作目录？

## 一条命令运行

在本分支的仓库根目录运行（需要 Python 3，仅用于查看原型）：

```sh
python3 scripts/run-history-prototype.py
```

打开 http://127.0.0.1:19877/?demo=1&prototype=history&variant=C 。可在命令末尾指定其它端口。正式 Windows 程序的打包方式不受影响。

底部左右箭头切换三种布局，URL 的 `variant` 分别为 `A`、`B`、`C`；非输入控件焦点下也可用键盘左右键切换。现有首页是原型宿主，仅专用启动器注入开启标记，普通程序不启用此界面。

| 方案 | 主要入口 | 适用问题 |
| --- | --- | --- |
| A 时间轴与双栏证据 | 选机器、点时间片；NPU 与 ps 并排 | 已经知道大概时刻，逐帧查看发生了什么 |
| B 疑似竞争事件列表 | 按事件进入，查看事件前一帧 | 快速找到同卡新出现的任务，再核对命令和目录 |
| C 多机时间矩阵 | 点击机器与时间交叉格 | 先浏览整批机器的历史，再下钻单次采样 |

## 可操作范围

- 16 台模拟机器、900 轮初始记录、4 秒采样间隔，覆盖 1 小时，共 14,400 份机器快照。
- 开始/停止模拟记录：每 4 秒追加一轮到浏览器内存。使用连续的模拟时钟，不是真实墙钟。
- 回放暂停、逐帧、1/2/4 倍速、时间轴、跟随最新。记录可以继续，手动选择旧帧不会被新增记录拉回最新。
- 同轮原始 NPU 输出、ps 输出、PID → 工作目录表；点击 PID 联动选中的任务。
- 采集缺失用问号和缺失提示，目录未取得单独提示，不用当前状态或上一帧伪造历史。
- 展开“查看原型状态 / 数据模型”查看相关状态，切换布局保持机器、时刻与 PID。

所有机器、PID、目录和输出均为生成的模拟数据；不连接 SSH、不读取真实凭据、不保存历史，刷新重置。演示仅包含 NPU 0，未验证真实型号的 npu-smi 输出解析，也没有生产记录接口。

## 快速体验

1. A 默认 ascend-01 / 14:00:40。同卡 PID 4101 与 7702 对应不同工作目录，点击两者看联动。
2. 14:01:00 的 PID 7702 在读取 cwd 前退出：保留 NPU/ps 观察，目录显示未取得；下一帧不再出现该 PID。
3. B 选择 ascend-04 的事件，再点“看事件前一帧”：从两个 PID 回到一个 PID。
4. C 点击 ascend-02 / 14:00:44：显示整帧采集缺失，不能解释成没有任务。
5. 停在旧帧后开始模拟记录，等待超过 4 秒：快照计数增加，选中时刻不变。点击“跟随最新”才跟随新记录。

## 目前结论与验证边界

浏览器中已经验证三种布局切换、事件前一帧、PID 目录联动、整帧缺失、cwd 缺失、4 倍速回放到末帧，以及模拟记录增长而旧帧保持。已观察到 384 → 512 份快照增长，选中时刻保持在 14:00:44；桌面 1440×1000 与窄窗口均查看过。JS 语法检查通过。

用户已选择 C 多机时间矩阵作为方向，并补充要求：记录自定义指令、兼容 watch 输入，运行时不能依赖 AI。当前已在 C 中验证这些交互；仍然不是正式采集功能的验证。原型代码只作为需求与交互的第一手材料，不直接合入 main。

## 正式实现需要保留的证据

一次机器采样应保存机器稳定 ID、sample ID、采样起止时间，以及各命令自己的采集时间/错误；绑定原始 `npu-smi info`、完整 `ps -ef`、涉及 PID 的 `/proc/<pid>/cwd`。不要只保留筛选 Python 后的进程列表。

`ps -ef` 本身通常没有工作目录，所以 cwd 必须在采样时额外取得并存档。PID 会复用，关联还需机器 boot ID 与进程 starttime，并检查采集过程中的身份变化；原型展示这些字段，但没有实现真实采集校验。多条命令不是原子快照，应保留它们的时间跨度。进程提前退出、权限问题和断线必须保留缺失，不能回放时再查当前机器补齐。

同卡多 PID 只说明疑似竞争，合法协同任务也可能有多个进程。目录和命令帮助定位任务；大家共用 root 时不能仅据此确定具体人员。真实落地还需验证设备输出中的 PID、容器 PID/目录命名空间，以及采样间隔内短任务漏采的情况。

生产阶段另行实现本地持久化、记录范围、容量/保留期限、历史查询与重启后回放，评估全量 ps/cwd 采集成本和真实 SSH 结果。当前没有实现这些能力。

## 方案 C 的后续确认：自定义指令与无 AI 规则

用户确认 C。矩阵可以选择任一已保存指令，内置 NPU / 完整 ps 作为固定辅助证据，自定义指令可多次添加并勾选记录。每个快照保存当时的指令名称、原始输入、转换后的单次命令、stdout、stderr、退出码及采集时刻。新加指令只出现在后续记录，不能补造旧帧；停止记录也不删除已有结果。

自定义指令默认“不判断，仅记录”。可选“包含指定文本”“相比上一帧变化”，都是浏览器本地确定性计算，完全没有 AI、模型或外网分析。输出为空但命令执行完成，和 SSH 采集失败是不同状态；例如 grep 未匹配时保存空 stdout 与退出码 1。

NPU 模式演示用固定格式解析器从模拟原始输出提取 NPU 0 的不同 PID 数量，超过 1 才标记。它仅支持原型数据格式，不能宣称已兼容真实设备输出。同卡多进程、关键字命中或文本变化都不能自动定性为任务挤占。任意自定义输出不自动推断 PID/目录。前一版本的竞争时间段是预设模拟场景；本次 C 的格子由所选规则计算，原始场景仍是模拟数据。

watch 兼容预览支持常见 watch、-n / --interval、-d / -t / -c / -p 和对应长选项，剥离单层外部引号，保留命令内部管道；未知选项、复杂外层引号不静默猜测，提示改填单次命令。这是受限语法预览，不是通用 shell 解析器。正式实现应在服务端解析并保存原始与规范化命令，不能直接把无限循环 watch 当单次 SSH 任务。

当前统一每 4 秒采样，watch 指定的间隔在转换后明确显示，不暗中沿用。不支持的选项应要求用户填写内部命令，而不是尝试执行其它内容。真正落地时仍需完成服务端规范化、采集与持久化；现有 main 的配置校验还会拒绝 watch 输入。

本次浏览器交互验证包括：tilexr 文本匹配命中/不命中；grep 空输出且退出码 1；添加 `watch -n 2 'tail -n 20 /tmp/job.log'` 后正确显示单次命令与 4 秒统一采样提示；新指令的旧帧显示未记录。所有验证均使用模拟输出。

## 一小时历史与局部放大

方案 C 的初始模拟数据扩展为 14:00:00 至 14:59:56 的 900 轮，时间覆盖区间显示为 14:00:00–15:00:00。16 台机器合计 14,400 份快照。模拟事件每 20 分钟重复，方便检查中后段跳转；不代表真实观测。

矩阵提供 1 分钟、5 分钟、15 分钟、1 小时四档范围。整小时使用 60 列，每格汇总 15 个原始帧；一分钟放大则显示 15 列，每格一帧。其它档位每格最多 2 / 4 帧。前后时段按钮浏览相邻范围，原有滑块仍可定位全局任意帧。

汇总优先显示规则命中，其次缺失/无法判断，最后正常记录。提示同时给出命中帧数与缺失帧数；点击优先定位首个命中帧，未命中则定位首个缺失帧，否则定位第一帧。放大按钮以当前选中帧所在分钟为中心入口。汇总只改变展示，不丢掉原始输出，也不对判断结果求平均。

浏览器已验证 900 轮 / 14,400 份初始记录、整小时仅渲染 960 个数据格（16×60）；点击 14:40 的命中格定位到 14:40:32；放大后显示 14:40–14:41，共 240 个数据格（16×15）。这验证的是预装模拟记录的浏览与回放，不是连续运行一小时的真实 SSH 采集、落盘容量或稳定性验证。正式实现仍需按时间范围查询历史并设置容量/保留期限。
