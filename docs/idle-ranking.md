# 空闲机器排序与 JSON 导出

v0.8.0 提供五档历史偏好，结合当前 NPU、HBM 和中台占用检查，为预计使用不超过一小时的任务提供候选顺序。发现能力为 `idle-machine-ranking-v1`。排序不预留资源，不更改现有 `ready` 或自动提交的定义；未指定机器的旧提交接口仍按 ID 选 ready 机器。需要按本排序选择时，AI 必须明确选定机器并通过原预约/提交协议操作。

## 页面与五档

点击顶部“空闲机器排序”。表格显示历史档位、当前资源条件、最近 5 分钟及 1/2/3/4 小时占用比例与覆盖率、设备数、每设备最少空闲 HBM 和 NPU 采样时间。支持机器组、精确型号、每机设备数及 HBM 条件。页面打开时每 10 秒读取最新监控快照，失败时清空旧结果。

| 档位 | 从高到低匹配，首次命中 |
| --- | --- |
| 1 | 最近至少 3 小时，已观测占用时长为 0 |
| 2 | 最近 2 小时，已观测占用时长为 0 |
| 3 | 最近 1 小时，已观测占用时长为 0 |
| 4 | 最近 1 小时占用非零且低于 15% |
| 5 | 最近 1 小时占用至少 15%、低于 25% |

历史不足、保存异常或最近 1 小时占用至少 25% 返回 `tier: 0` 和明确的 `historyReason`。零占用采用未四舍五入的占用毫秒数，不能把显示 0.0% 当作零占用。前三档按对应窗口每个小时的覆盖率均至少 90% 才成立。≥4 小时不会增加档位；同档按机器 ID 稳定排序，没有额外预测分数。

`eligible` 只表示本次当前资源检查通过；`recommended` 要求 `eligible` 且历史档位 1–5。只有推荐机器获得正整数 `rank`。当前符合但历史不足的机器单独保留，不能谎报长时间空闲。排序顺序是推荐机器、当前符合但未分档机器、当前不符合机器。

## 5 分钟统计与启动积累

复用原 `npu-smi info` 采样，无额外 SSH 轮询。任意设备有 NPU 进程就计整机占用，包含算力为 0 的进程。进程表未知、命令失败或截断不补零；前值估计仍最多延续 `2 × 采样间隔 + 30 秒`，与小时历史采用同一积分区间。

以 5 分钟为桶，保存已知进程状态毫秒数和占用毫秒数，不保存 PID、进程名或单卡历史。只用完整桶，因此实时 API 的 `historyThrough` 为最近一个 5 分钟边界；在整点/半点可以准确聚合之前 1/2/3/4 小时，不按比例拆分自然小时桶。覆盖率分母为完整请求窗口，未知时长降低覆盖率；所有比例按对应观测时长加权。

`occupancy/recent.json.gz` 原子保存，保留最近 6 小时，压缩文件最多 64 KiB，解压读取上限 2 MB。每分钟保存，正常退出保存，异常掉电可能损失最后不足一分钟。重启保留已完成的桶，不延续停机前的采样。SSH 地址、物理资源键、机器 ID 或型号变化不继承旧身份的空闲优先级。

升级前只有自然小时桶，不能还原 5 分钟历史。新版本开始后通常积累约 1 小时，才可能出现第 3/4/5 档；积累约 3 小时，才可能出现第 1 档，实际取决于覆盖率与边界。覆盖 ≥90% 仍可能有未知时间，所以称“观测零占用”，不称严格连续无人使用。

## 当前资源条件

实时 API 每次重新读取本机监控和中台占用，不主动连接远端。要求机器启用、NPU 监控启用、SSH 监控新鲜在线、无中台任务/预约/等待单持有或清理操作，且 NPU 样本来自当前入口及物理身份，退出码为 0、无错误警告、未截断、所有设备及进程表完整。

所有设备必须无 NPU 进程，利用率为 0；并按请求检查精确型号、设备数和每设备最少空闲 HBM。默认每设备至少 1024 MB 空闲 HBM，不限制型号和设备数，样本最大年龄为 `min(120, 2 × 监控间隔 + 30)` 秒。这只是默认筛选条件，AI 必须按实际任务提供 HBM、型号和设备需求，不能认为默认条件证明任务能运行。设备数为 `npu-smi` 中可识别设备/芯片行数。

## 自动文件与只读 API

启动完成时生成一次，之后北京时间整点、半点重算并原子替换：

```text
<discover返回的dataDir>/exports/idle-ranking.json
```

文件最多 128 KiB，不逐轮追加；文件权限 0600。64 KiB 历史与 128 KiB 导出另设固定上限，原子替换期间还会有同等大小临时文件。保存失败保留旧文件，API/页面返回 `exportError` 与原 `exportedAt`，最长一分钟后重试；不因此停止监控。新增历史格式损坏会阻止启动，应保留文件交由维护者诊断，不能删锁绕过。

`GET /api/idle-ranking` 使用正常会话令牌与 `X-Watch-Instance` fencing。支持可选查询：

| 参数 | 范围 |
| --- | --- |
| `group` | 机器组精确匹配 |
| `model` | 每设备型号精确匹配 |
| `devicesPerMachine` | 1–128 |
| `minFreeHbmMB` | 0–1099511627776，MB |
| `maxSampleAgeSeconds` | 1–300 |

API 每次聚合最新完整 5 分钟桶并重新检查当前资源，不写导出文件；`generatedAt`、`historyThrough` 与自动文件的 `exportedAt` 分别返回。自动文件使用默认资源条件；“下载当前 JSON”下载当前筛选的 API 结果。

响应包含 `schema: "simplehtmlwatch.idle-ranking.v1"`、`rankingPolicyVersion: "five-tier-v1"`、实例/serviceId/runId、生成时间、历史截止、下次自动保存时间、导出路径/错误、历史容量、资源条件和全部机器行。每行包含 `machineId`、`resourceKey`、组、型号、档位、历史原因、五个 `windows`、`eligible`、`recommended`、`currentReason`、`resourceCheckedAt`、`lastNpuSampleAt` 及 HBM。没有凭据、会话令牌、完整配置或原始命令输出。机器名称与资源标识可能包含内部地址，文件按本机授权范围分发。

`requiresLiveCheck: true` 始终存在。文件超过下一次更新时间、实例身份不匹配或资源采样过期时，不能据此直接运行。即使刚生成，文件也只提供候选顺序，实际领用前仍应通过同一实例实时查询并申请原预约；多个入口须按 `resourceKey` 与原资源冲突协议避免重复占用。只有后续授权的任务请求才执行远端命令。

## AI 客户端

两个客户端均先 discover 校验同一实例，缺少能力只报错，不重启或换构建：

```sh
python3 skills/cluster-task-controller/scripts/taskctl.py --instance <实例名> discover
python3 skills/cluster-task-controller/scripts/taskctl.py --instance <实例名> idle-ranking --group "<机器组>" --model "<型号>" --min-free-hbm-mb 32768
python3 skills/simplehtmlwatch-netdata/scripts/metricsctl.py --instance <实例名> idle-ranking --group "<机器组>" --devices-per-machine 16 --min-free-hbm-mb 32768 --max-sample-age 90
```

示例的设备数和 HBM 仅演示参数，须按实际硬件与任务修改。返回 0 表示读取成功，候选为零或启动积累历史也可返回 0；返回 3 表示历史保存或自动导出异常，有效部分仍可阅读；身份、协议、参数或请求失败返回 2。查询不会预约、提交、清理进程或改变默认自动调度。

## 验证边界

确定性测试覆盖五档及 15%/25% 边界、毫秒非零、每小时覆盖率、跨午夜桶、失联/重启不补齐、入口和物理身份变化、实时进程/显存/型号/设备数/预约门禁、半小时定时、导出失败、私有文件和容量。浏览器测试使用合成数据验证展示、筛选、JSON 下载、自动检查、失败清空与窄屏。它们不证明未来一小时无人使用，也不等于真实 NPU 工作负载性能验收。
